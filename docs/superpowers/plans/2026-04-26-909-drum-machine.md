# 909 Drum Machine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an Await large widget that runs a 16-step, 4-row drum machine using the built-in 909 soundfont (`/assets/sounds/909.sf2`, GM bank 128).

**Architecture:** Single-file TSX widget. State persists in `AwaitStore` (no React state, no closures). Audio plays through `AwaitAudio.playNote` with `delay` to schedule 8 measures of notes upfront when play is pressed — the iOS native audio engine sequences them, the widget JS does not need to run continuously. Visual playhead is computed each render from `(Date.now() - playStartedAt) / stepDurationMs` and refreshed by a fast-update widget timeline.

**Tech Stack:** TypeScript, TSX, Await widget runtime (`'await'` import), `AwaitStore`, `AwaitAudio`. Bun is used only for `bun install` and running the typecheck (`bun run test` → `tsc --noEmit`).

| Key             | Type        | Default              | Purpose                                                   |
|-----------------|-------------|----------------------|-----------------------------------------------------------|
| `cells`         | `boolean[]` | `Array(64).fill(false)` | Flat 4×16 grid, indexed `row * 16 + col`                |
| `bpm`           | `number`    | `120`                | Tempo in beats per minute                                 |
| `playing`       | `boolean`   | `false`              | Whether sequencer is currently playing                    |
| `playStartedAt` | `number`    | `0`                  | `Date.now()` at the moment step 0 started; `0` if reset   |

Persistence is automatic — patterns survive widget restarts (this is desired UX).

## Design Decisions for v1 (please confirm before implementation; small, reversible)

1. **Note mapping (rows top → bottom):**
   - Row 0: Open Hat (MIDI 46)
   - Row 1: Closed Hat (MIDI 42)
   - Row 2: Snare (MIDI 38)
   - Row 3: Kick (MIDI 36)
   (User specified bottom → top: kick, snare, closed hh, open hh.)

2. **Playhead visualization:** ALL 4 cells in the current step column turn green while the playhead is there (classic LED-column behavior). Activated cells in that column display as green during playhead pass-through, then revert to yellow. Non-activated cells in that column also briefly show green. This makes the playhead visible regardless of which rows have activated cells.

3. **Pause behavior:** Best-effort stop. Pre-scheduled audio within the current 8-measure batch may continue for a few seconds because there's no documented API to cancel scheduled `playNote` calls. We attempt `AwaitAudio.setAudioSession(false)` to mute the session.

4. **Resume after pause:** Play always restarts from step 0. Pause+play is effectively a restart. (Resume-from-position is a v2 enhancement.)

5. **Edits during playback:** Cell toggles and BPM changes update state but DO NOT alter the already-scheduled audio batch. Changes take effect on the next play press. Visually the cell color updates immediately when toggled.

6. **Scheduling horizon:** 8 measures = 128 steps queued upfront on play. At 120 BPM that's ~16 sec; at 60 BPM ~32 sec. After this, audio stops; the user must press play again. (Re-scheduling from the timeline is a v2 enhancement.)

7. **Widget family:** Designed for `large`. Other families may have layout overflow; no fallback shipped in v1.

8. **BPM range:** 40–240, step ±5. (Tunable via `@panel` constants.)

9. **Audio scheduling unit assumption:** `AudioConfig.delay` is assumed to be in **seconds** (consistent with iOS audio APIs). If on-device testing reveals it is milliseconds, divide the conversion by 1000 in `scheduleLoop()`.

10. **Strict squares + flex layout (per user direction).** Cells are exact squares whose pixel size is computed once per render from `entry.size.width`. The widget body is a vertical `VStack` with three children: `TopBar` (top), `Spacer` (flex middle, may be empty), and the grid `VStack` (bottom). This leaves room to add 1–2 more rows later without redesign.

If any of these are wrong, please flag before Task 1 begins.

## Helper Math (planned, finalized in Tasks 2 / 9 / 10)

```ts
function stepDurationMs(bpm: number): number {
  // 16th notes at 4/4
  return 60_000 / bpm / 4;
}

function currentStep(bpm: number, playStartedAt: number): number {
  if (!playStartedAt) return -1;
  const elapsed = Date.now() - playStartedAt;
  if (elapsed < 0) return -1;
  return Math.floor(elapsed / stepDurationMs(bpm)) % STEPS;
}

function computeCellSize(widgetWidth: number): number {
  // 16 cells per row, 3 group gaps + 12 inner gaps + left/right padding
  const usable = widgetWidth - 2 * PADDING;
  const totalGaps = 3 * CELL_SPACING_GROUP + 12 * CELL_SPACING_INNER;
  const cellWidth = (usable - totalGaps) / STEPS;
  return Math.max(8, Math.floor(cellWidth));
}
```

function scheduleLoop(cells: boolean[], bpm: number) {

## Open verification items (for on-device testing — not part of any task)

1. **`AudioConfig.delay` units.** This plan assumes seconds. If notes fire too fast (delay is treated as ms), `scheduleLoop` needs `(measure * STEPS + step) * stepDurationMs(bpm) / 1000` replaced with `(measure * STEPS + step) * stepDurationMs(bpm)`.
2. **Cancel-on-pause behavior.** If `setAudioSession(false)` does NOT silence pre-scheduled `playNote` calls, pausing while a long batch is queued will leak audio. Mitigations: reduce `MEASURES_TO_SCHEDULE` to 2–4; or document the tail explicitly.
3. **Refresh rate of `update: new Date()`.** If the playhead visualization is too choppy on-device, no widget-side fix exists — iOS caps widget refresh budgets. Document the limitation.
4. **Widget family fallback.** The widget assumes `large`. If it appears on `medium` or `small`, the grid will overflow. Add a family check in `widget()` returning `<Text value='Add as Large'/>` if `entry.family !== 'large'`. Out of scope for v1.
